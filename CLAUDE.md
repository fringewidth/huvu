# huvu

An agent chat app. The core idea: the whole UI is a canvas built with p5.brush. As the agent talks, flowers grow in. The canvas is the last thing to build, since it needs a palette decided first, and it's the most creative part.

Talks to an agent called Hermes on the backend. Used by one family: each person is a user, and shared devices (the TV, speaker hardware still to be built) belong to a group, the household by default. Hosted on the web, and installed as an app on phone and Fire TV.

## Platforms and priorities

1. Phone (Android): the daily driver. Needs the most native flexibility: wake word, widgets, fast cold start. This is the platform to optimize hardest for.
1. Web: hosted, full-featured, same codebase as phone.
1. Phone (iOS): minimal, chat only. Built for the owner's mom. Platform limitations here (see wake word below) are accepted, not worked around. Since 2026-10-11 it is the web build added to the home screen, with no app (see push notifications below).
1. Fire TV: display only, the largest screen, so it gets the most design care. It has no composer and no flower. It shows the turns of its own conversation and the live feeds picked on it with the remote (Menu opens the list, which also says who is here), and huvu says every answer aloud (`speaksAnswers`, `voice/useSpokenAnswers.ts`), since the person is across the room. Fire TV gives apps no mic, all checked on the family's Stick over ADB on 2026-10-10. The remote's mic button goes to Alexa, and no app can catch it or remap it. Fire OS takes `RECORD_AUDIO` from every app that lacks `com.amazon.permission.ACCEPT_VOICE_INPUT` (`signature|amazon`), so the audio server refuses to record for huvu even though Android lists the permission as granted, and a USB mic is most likely refused the same way. Amazon's speech recognizer (`com.amazon.vizzini`) is `signature|system`. The system keyboard does dictate ("Press and hold to say words and phrases"), but only for accounts in the US, UK, Germany, France, Italy, Spain and Japan and a few locales (`arcus_speechtotext_restrictions_config.json` in `com.amazon.tv.ime`, refreshed daily from Amazon), and the Stick's account is Indian. So asks come in through a custom Alexa skill: "Alexa, ask my huvu ...". The skill stays in development stage (decided 2026-10-10), so it needs no review and works at once on every Alexa device of the account that made it, which is the Stick's own Amazon account; it is `huvu` in that account's Alexa developer console, with English (IN), invoked as `my hoover` (since 2026-10-11; Alexa's speech recognition writes only words it knows, so a spoken `hoo voo` came out as "who", and `who view` failed too; "my huvu" said aloud is heard as `my hoover`, and the `my` makes it the two words Amazon asks for; the app and the docs write it "alexa, ask my huvu", with `my` in lower case), and its interaction model is `docs/alexa-interaction-model.json`: one intent whose catch-all custom slot takes the whole sentence, since a custom slot passes on what Alexa heard word for word, and its values only steer the hearing (`AMAZON.SearchQuery` needs a lead-in word in every sample, which Alexa strips from the slot). Alexa posts each ask to `POST /api/alexa` (`backend/src/huvu/alexa.py`): the backend checks Amazon's certificate chain and signature, the timestamp and the skill's id (`HUVU_ALEXA_SKILL_ID`, in `compose.yaml`), asks it as a spoken ask in the conversation of the household TV that has its push stream open (the one paired last, if several), and answers Alexa at once with silence; with no TV showing huvu, Alexa says so. The TV shows the turn and says the answer. The gateway is to bring the app to the front over ADB (see stack decisions), not built yet, so for now huvu must be open on the TV. Alexa can't be taught a word: it turns speech into text before it picks a skill, and a skill's model steers only what comes after the name. So pick a name by what Alexa's voice history shows it heard ("Alexa, open huvu" is heard as Hulu). On launch, the empty stage shows one greeting picked at random, with an example Alexa ask under it (`greetings` in `interaction.ts`). Treated as its own build target.

## Stack decisions and why

1. **Frontend shell: Capacitor, not React Native.** p5.brush only exists as a browser Canvas2D library, and the flower visuals must look identical across web, phone, and Fire TV. Porting p5.brush's stroke/noise rendering to a native engine (react-native-skia) was priced out as a multi-month job with ongoing visual-drift risk, worse than the cost of any Capacitor limitation. Capacitor wraps the same web app for every target, so there's one implementation of the canvas, not several that have to be kept in sync.
1. **Chat state: a small hand-written store, not assistant-ui.** `frontend/src/chat/thread.ts` holds the conversation as turns (one ask and what huvu did with it), since the stage shows turns and never a chat log. assistant-ui was used at first, for its thread runtime only; it was dropped because it was more than half of the startup bundle (602 KB down to 335 KB) and every turn had to be derived from its messages on each change. Edit is rewind: it replaces the turn and everything after it, with no branches kept. The store mints each turn's id and sends it with the ask, so the backend keeps the same id. Each turn has its own stream: stop asks the backend and keeps reading until the turn ends, and a turn the store has no stream of (one running across a restart, one the device didn't start) is followed from its start (`GET /api/turns/{id}/events`), since a delta can't be added to a snapshot. The store catches up from `GET /api/conversation` each time the push stream connects. The backend calls, Server-Sent Events streams, live in `chat/backend.ts`.
1. **Backend: Python (uv, asyncio, Pydantic, FastAPI, SQLite), not Node or Bun.** JS/TS everywhere was the first pick, to avoid a language switch when reviewing code. It was reversed on 2026-10-03: the backend will need ML pieces that ship as Python first (face embeddings, speech, vision), Hermes is Python and its plugins are too, and the tested Tuya code is Python. The backend stays one language. Its job: an interface to data (pluggable sources and their tables, triggers over them, the action policy), exposed to Hermes over MCP, and the link to the frontend (sessions, turning Hermes output into parts). Memory and skills belong to Hermes; the backend owns every text the model reads from huvu (`prompts.py`, see Prompts) and picks the model for each run (see the tiers). It does own every schedule, since triggers are the only scheduler (see below). Design: `docs/backend-architecture.md`. The frontend side: `docs/frontend-contract.md`.
1. **Hosting: one container on the Windows host, published by a Cloudflare Tunnel.** Decided 2026-10-08. The host is a Windows machine for good, under Docker Desktop. The image (`Dockerfile`) is built on Hermes's official `nousresearch/hermes-agent`, so Hermes keeps its own runtime and s6 supervision. It is pinned by digest to the 2026-09-24 build (pinned 2026-10-09): the 2026-10-08 build shipped without uv and without aiohttp, so its API server never started. Moving the pin is a change of its own, checked with an ask end to end. In the image, Hermes's gateway is the main process, huvu's backend an s6 service (`docker/s6/huvu`), and `docker/cont-init/50-huvu` writes the skills (`huvu skills`) and runs `setup.sh` on every start. One volume, `/opt/data`, holds Hermes's profiles and logins and huvu's config, data and secrets (`/opt/data/huvu`, through `HUVU_CONFIG` and `HUVU_ENV_FILE`); a Docker volume, not a Windows folder, since SQLite over the Windows file share is slow and locks badly. The house's timezone is `HUVU_TIMEZONE` (Asia/Kolkata unless `./setup.sh --timezone <IANA name>` says otherwise), set for huvu and every Hermes profile, since the container's own clock is UTC. `compose.yaml` publishes it on the host only (`127.0.0.1`, port 27613, picked at random so it collides with nothing; `HUVU_PORT` moves it), and the host's own `cloudflared`, already running for other services on `hrishik.me`, publishes it at `https://huvu.hrishik.me` (a public hostname on the existing tunnel, service `http://host.docker.internal:27613`, since that cloudflared runs in a container of the immich project, where localhost is the container itself). No port is opened at home, and phones need nothing installed. The backend serves the web build there too (`HUVU_WEB_DIR`, built in the image's first stage), so one address is both the app and its backend. Every build, web, phone and Fire TV, talks to `https://huvu.hrishik.me` (decided 2026-10-09), and no code names it (since 2026-10-14, so the repo can be shown without pointing anyone at the owner's data): it is `HUVU_PUBLIC_URL` in the gitignored `.env` next to `compose.yaml`, which the backend, the image's phone bundle, the phone build (`vite.config.ts`) and the TV app's build (`tv/build.gradle`) read; the web build and the TV's page use their own origin, and the Chrome extension takes the address in its options. Only Vite's dev server reads `VITE_BACKEND_URL`, for a backend on the dev machine. Hermes's API server stays inside the container. Tailscale Funnel was the first pick (free, no domain) and was swapped for Cloudflare the same day; plain Tailscale would put every phone on a VPN. Like any tunnel, it carries no WebRTC, so live feeds will need another route. A slim image (Python 3.14, Hermes from source with only huvu's extras, 822 MB against about 4 GB) was tried and dropped: Hermes's package manager didn't recognize the install and built its own runtime, without the API server. The image was built and run on the dev Mac (arm64) on 2026-10-08: the gateway, the backend, MCP, the plugin, skills, soul and a user's profile all came up, and an ask reached Hermes. On 2026-10-09 it was built and run on the Windows host (`ssh laptop` on the home network, the repo at `D:\huvu`; notes in `hrishik.md`), behind the tunnel: from outside, the web client loads, login works, and every route that reaches Hermes, Groq or the house answers 401 without a device's token. Login allows 10 wrong passwords per address in 15 minutes (`LoginLimit` in `auth.py`, by Cloudflare's `CF-Connecting-IP`); a Cloudflare rule was passed over, since the free plan's one rule only counts 10 seconds and blocks for 10. Asks failed there on the 2026-10-08 Hermes. On the pinned image, an ask through the tunnel streamed Hermes's answer back the same day. After a start, Hermes's API server comes up about 20 seconds after the backend, and an ask in that window fails. The host builds its own image from `D:\huvu`, pulled from GitHub with a read-only deploy key. A workflow that published the image to the repo's package on every push was removed on 2026-10-10, with the package: nothing pulled it, since Docker on the host can't log in to a registry over SSH. The commands for the host are in `hrishik.md`.
1. **Data: everything is SQLite, everything is a table, and the agent learns preferences from it.** Decided 2026-10-06; everything read through SQL since 2026-10-09. huvu's agent is expected to learn each person's preferences on its own, mostly in the nightly dream, through real data engineering over the house's history. Every source declares its tables in its spec, in two kinds. History tables hold what happened: the source records typed rows (`ctx.record`), the kernel keeps them all in one SQLite file (`data/analytics.db`), adds the same id, time and person columns to every row, and keeps them for good. Live tables hold what is true now (`ha_entities`, `location_people`, `huvu_mode`): the source hands the kernel its rows (`ctx.replace`, `ctx.put`, `ctx.drop`, `ctx.unavailable`), and the kernel checks them, keeps them in memory and serves them to queries as SQLite virtual tables in APSW. Drivers are untrusted: they only hand over data, and the kernel never calls into one to answer a query, owns the copies queries read, and nudges triggers itself. Every SQLite file in the backend is opened through APSW (`db.open_db`), and Python's `sqlite3` isn't used at all, since two copies of SQLite in one process can corrupt a shared file. `data_sql` is the model's only read tool: one read-only, caller-scoped query over every table, so one query can join sources, history and now alike. Values, the event log and its tools (`state_get`, `state_search`, `events_search`, `events_digest`) were removed on 2026-10-09: a source's events were always rows of its history too. The kernel's own log is `huvu_events`, and every conversation turn is a `chat_turns` row (the built-in `chat` source), so a fresh session that only gets the latest 50,000 characters of transcript reads the rest there. A source's skill lists its tables. No other database engine is used; extensions cover the rest (FTS5, JSON, `sqlite-vec` later). Non-tabular data (images, audio) stays in its source, and the rows hold facts about it with a ref. Design: `docs/backend-architecture.md`, Tables.
1. **Triggers are the only scheduler; Hermes cron is off.** Decided 2026-10-07. A Hermes cron job made from the API server has nowhere to deliver its output, costs a model turn on every run, and never shows in the app. So `setup.sh` turns off Hermes's `cronjob` toolset in every profile, and anything at a time or on a change is a huvu trigger. A trigger is one read-only SQL query and a script (decided 2026-10-09): `fire: edge` runs the script when the query's answer goes from no rows to some rows, `fire: rows` for each new history row (by `id`), and `once` ends it after the first fire. `skip` makes it skip its next fires (`triggers_skip`, "skip next" in the menu; added 2026-10-16): each runs no script, so "not tomorrow" needs no timed pause, and moving one occurrence is a skip and a `once` trigger. Every day at 8 is `SELECT 1 WHERE now_minute() = 480`. A query runs at once when a table it reads changes (a row recorded, or a live table's rows handed over; the kernel nudges itself, so none is missed), and every minute when it reads the time. What it reads is found from SQLite's authorizer when it is compiled. `triggers_register` with `dry_run` shows the answer now and what the script would do. Every trigger is a script (decided 2026-10-08): it does what needs no thought itself, such as a reminder through `huvu_notify`, with no model call, and starts a model instance with `ctx.wake(...)` when it needs one. The model learns when to wake itself by writing the script, so no prompt teaches it. A trigger that fires more than 30 times in 5 minutes, or wakes the model 20 times in two hours, pauses itself. The nightly dream is a daily trigger too, one per person, waking in their own profile: the kernel sets it up for every user (`dream.py`, `[dream]` in `huvu.toml`, 04:00 on pro by default, up to an hour), its note is the dream prompt, and it ends with a brief to its person through `huvu_notify`, written as quick notes. It acts on what it noticed: it guesses what its person wants, does the legwork (the web, subagents), and asks about it in passing in the brief, and the reply reaches the chat with the question (see the router). It sets up, unasked, the triggers it judges would help its person, and the brief names each one. Its prompts and `SOUL.md` push it to guess and act, since the first wiki-era dream (2026-10-13, on gpt-6-sol) noted a bonsai search as "a curiosity, never assume", inferred nothing, and stopped after 5 of its 60 minutes. A removed dream stays removed; a live one is rewritten in place when the code changes it. Only its person can pause or remove a dream, from the app, and the model gets a refusal (since 2026-10-14, when a dream run on the day's manual 11:25 fire judged its own time wrong, copied itself into an ordinary trigger at 04:00 and removed the real one). Design: `docs/backend-architecture.md`, Triggers.
1. **Memory: the agent's own wiki, which it organizes and searches itself.** Decided 2026-10-13, after the first dreams learned little: the owner's profile loaded only two of its five skills (`setup.sh` had refreshed only the default profile on start; now every profile, every start), the dream prompt named two tables, and Hermes's `MEMORY.md` holds 2,200 characters. Each profile's memory is a folder of Markdown pages, `<profile home>/wiki`, written with Hermes's own file tools, and its index is `MEMORY.md` (cap raised to 10,000), always in the prompt. A wiki in Karpathy's sense: one small page per subject, every mention of another subject a `[[wikilink]]`, and `dreams.md` as the log. The first dream, told only to "link pages that relate", wrote four topic essays with three links, so the dream prompt now spells the shape out. The pattern is Karpathy's LLM Wiki: the tables are raw sources the model only reads, the wiki is the model's, and a short text gives the conventions (the guide in `prompts.py`). No schema, no embeddings, no automatic recall: the owner's view is that models will keep getting better at managing their own memory, and a fixed design would hold them back. Hand-built stores (a claims table modelled on Meta Muse's, Hindsight, Mnemosyne) and hwiki's per-turn recall were considered and left out. The dream prompt states intent only: read every source, infer and chase hypotheses over nights, tend the wiki as its librarian, use any tooling, ask for features on `requests.md`, then set triggers and brief. Wakes go through Hermes's `POST /v1/runs` with the situation block as history, so `delegate_task` subagents run inline and return within the wake; on a session's chat stream Hermes would hold their results for a next turn that never comes. The person reads and edits the wiki in the app (menu, "wiki"; `components/Wiki.tsx`, `wiki.py`); an edit names the version it started from, so it never lands over the agent's change. Design: `docs/backend-architecture.md`, What Hermes owns.
1. **Three model tiers: basic, pro, advanced.** Decided 2026-10-08. `[models]` in `huvu.toml` maps them to `gpt-6-luna`, `gpt-6-sol` and `gpt-6-astra`, all on the ChatGPT login Hermes uses (astra is account-gated; it answered on this account). A tier is a model on the profile's own login, or a model and a Hermes provider (`pro = { model = "claude-sonnet-5-5", provider = "anthropic" }`), so tiers can move to the Claude login, or mix logins, without code changes; moving every profile's default login is `hermes model` on the default profile, then `./setup.sh` again for each user. The backend picks the model per run (`model` and `provider` on Hermes's session chat): a conversation's asks run on the tier the router picks (next), pro when it can't, a trigger's wakes on the trigger's `tier`, basic by default; the model that writes the trigger picks pro when the wake needs more thought. Advanced always needs its person's yes, wherever the trigger was set (a conversation, a wake, a dream): it waits as `awaiting`, a card goes to their phone for a day (`huvu.activate_trigger`, `requires_human`), a tap of "allow" in the menu on their own device also counts, and a no or no answer drops it. Each wake is its own Hermes session, so a wake's model never touches a conversation's prompt cache.
1. **The router: Clef-flash decides between a one-off on basic and pro with the conversation.** Decided 2026-10-10. A first version that day ran a whitelist of house words on basic; it was a bag of words with no order, so "turn off the projector in a bit", "put it on the projector" and anything inside "play ... on netflix" passed it, and it was removed. A second ran "turn on <device>" and the like with no model, matching devices in the kernel by HA's column names and argument shapes; it was removed the same day as an inversion of control (the kernel read a driver's conventions), until a cleaner contract is designed. Now every ask goes to Clef-flash (`@cf/cloudflare/clef-flash`, Cloudflare's decision model on Workers AI, free up to 10,000 Neurons a day) with one yes-or-no question (`ESCALATE_QUESTION` in `prompts.py`): does the ask need anything said earlier in the conversation? Below 0.30 it is a one-off and runs on basic with reasoning off (sent as `model_options.reasoning_effort`) in a fresh Hermes session with the ask alone, used once: on 44 asks labelled by hand (2026-10-10), every ask that needs context scored 0.462 or more, and the one-offs scored up to 0.478, so a few one-offs ("it's stuffy in here", "how far is the airport") go to pro. A one-off that needs thought ("plan a movie night for saturday", 0.144) runs on basic too. Otherwise it runs on pro in the conversation's main session, as on an error, after 1 s (`[router] timeout`, a deadline on the whole call) or without `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_AI_TOKEN`. Clef-flash answers the same text the same way, so its answers are cached by the ask's words. The main session always runs on pro, and no other turn touches its cache. It must know every turn of the conversation: its next ask carries a note for each turn after the last one it ran (`quick_turn` in `prompts.py`), appended so the cached prompt holds; a fresh main session (cold, rewound) reads them in its transcript, cut to the latest turns that fit. A bench through huvu's real stack showed basic with reasoning off doing house commands as well as pro (18 of 20 direct and 18 of 20 multi-step, about 8 s to the first word). Ruled out: Hermes's own router (`smart_model_routing`, removed upstream on 2026-04-19, and huvu sends the model on every run anyway); changing effort mid-session (OpenAI's request-level effort rewrites the hidden system prompt, a full cache miss); TypeSafe's Jev (no free tier); a blacklist of words (every unforeseen phrasing leaked). Every `chat_turns` row keeps its route (`why`: one_off, context, failed, off or notes) and Clef-flash's probability. An ask with notes waiting for its device runs on pro in the main session without asking Clef-flash (`why`: notes, since 2026-10-13): every notification leaves a note on each of its person's own devices (`prompts.notified`), and a reply to one ("a juniper, under 2k") must reach the session that reads the note, which Clef-flash, seeing the ask alone, can't know.
1. **Speech: Edge's voices speak, Groq's Whisper hears, and both cost nothing.** Decided 2026-10-08, English only for now. Text to speech is Microsoft's Edge read-aloud voices through `edge-tts` (`en-US-AvaNeural`, `[speech]` in `huvu.toml`), the same provider Hermes defaults to: free, no account, Indian English, and no load on the backend's CPU. It is an unofficial endpoint Microsoft could close. `GET /api/turns/{id}/speech` streams a turn's answer a sentence at a time while huvu writes it, each sentence one MP3 clip as Edge made it, framed by its length (`speech.py`); the app decodes the clips itself (`voice/speaker.ts`). Decoding on the backend (`miniaudio`) was dropped: it had no build for Python 3.14, and MP3 is an eighth the size of PCM over a phone's data. Edge misreads huvu's name as written, so the voice says it as "hoo voo" (`SAID_NAME` in `speech.py`). While Edge is down huvu is silent, and its answers still show. Ruled out: Kokoro (`kokoro-onnx`, local; tried first, removed the same day for sounding too cheap), ElevenLabs (its free 10,000 credits a month is about 80 short answers), Gemini TTS and Groq's Orpheus (free tiers of 10 to 100 requests a day), and Google Chirp 3 HD and Azure (free tiers big enough, but each needs a cloud account with a card). Speech to text is Groq's free `whisper-large-v3` behind `POST /api/transcribe` (`hearing.py`, `GROQ_API_KEY`), with huvu's name, the speaker's (the device's user, or whoever is recognized at a shared device) and the family's in the prompt, written as a sentence that uses them, falling back to `whisper-large-v3-turbo` on a rate limit. The app records the ask (Opus at 24 kbps) and ends it on a pause (`voice/transcriber.ts`). Hands-free, the clip goes to be transcribed after 0.6s of quiet, during the 3s pause that ends the ask, so the text is usually back when the mic stops: from a phone, the round trip through the tunnel (Cloudflare routes it through Hong Kong, about 0.5s) and Groq (under 0.5s) took 1.6 to 2.6s after the pause (measured 2026-10-10). Speech after it was sent makes it stale, and the clip is sent again; on the web, Chrome's recognition runs alongside and stands in when Groq can't hear. No words show while you speak, only the final text once the ask ends: Chrome's live words were often wrong, and watching Whisper correct them distracted (removed 2026-10-08). The phone has no such fallback yet: Android's own recognizer through a Capacitor plugin is the plan. Hermes's own audio relay (in its dashboard server, not the API server) was looked at and not used: one more process.
1. **Home Assistant: huvu works every exposed device directly, and scripts are routines.** Decided 2026-10-06 as scripts only (most devices are infrared); reversed by the owner on 2026-10-09. Each exposed entity huvu can work (light, switch, fan, button, scene, media player, climate, vacuum, number, select, cover, lock) is one huvu action (`light.theatre_ceiling` is `ha_light_theatre_ceiling`), with arguments from its attributes, and `ha_entities.action` names it. Infrared devices become template entities in HA (a button per learned code), so they are worked the same way. Each exposed script is one action too (`script.bedroom_ac_set` is `ha_bedroom_ac_set`), for routines that work several devices, such as turning the home theatre's AV unit off. huvu's skill lists every exposed action, one line each: its call, then the name, area and aliases, with no how-to text, so each is one call with no search first (since 2026-10-10: with devices left out of the skill, the model searched first and then rebuilt the AV sequence by hand, 9 rounds for one ask). Each thing a person asks for is one exposed entity or script, and its waits and order live in HA. A label (`huvu_silent`, `huvu_notify`, `huvu_ask`, `huvu_human`) sets the autonomy: on a script, no label means ask; on an entity, its own label wins, then its area's, then its domain's default (silent for lights, switches, fans, buttons and media; notify for climates, vacuums and covers; ask otherwise). Locks, alarms, and garage, gate and door covers always need a tap. The HA layer is kept native (areas, aliases, template entities, one package file per room), so a new device needs no change in huvu. huvu reads only what is exposed to Assist, records who caused every change (huvu, an HA app user, an automation, the device), and picks up script changes without a restart. Driver: `backend/src/huvu_drivers/ha/`. Design: `docs/backend-architecture.md`, The Home Assistant driver. The HA side, for the agents that set it up: `docs/home-assistant.md`.
1. **Live feeds: the gateway lists them, and nothing opens until picked.** The gateway knows every feed that exists (cameras, huvu's browser, a screen) and publishes that list, so the model has it as context and the app can offer it. A listed feed is not an open one. A feed opens only when the model picks it in a tool call, which emits a `video_feed` part, or when the user picks it. This keeps bandwidth and decoders idle until someone wants a feed, and it fits the stage rule that only the turn on the stage holds its feed open. Face recognition, if the camera side does it, reaches the model as text context next to the feed. `GET /api/feeds` is the list. In the frontend, `chat/feeds.ts` holds the list, fetched at boot and again each time it opens. `components/Feeds.tsx` shows it as a `LIVE / n` control opposite the wordmark, text only, with no previews, since a preview would be an open feed. On a shared device the same list has a "who's here" section, for recognizing the person at it. Picking a feed only watches it, and huvu is never asked (`thread.watch()`): it makes a turn of its own with no ask, the feed's name as the answer and the feed as its one part. Such a turn has `Turn.feed` set and makes no call of its own. The next ask carries it to the backend as an action (`{text, at}`, such as "opened the live feed balcony"), which Hermes reads as context and never answers (`actionsAfterLastAsk()` in `thread.ts`). A reply still coming in keeps streaming into its own turn underneath. A feed opened by huvu in a tool call is a different thing: a `video_feed` part in huvu's answer, and what huvu says about it (who is at the door) is entirely up to the agent. Fire TV opens the list with its Menu button (`feedsKey` in `interaction.ts`).
1. **Doorbell: a snapshot per press, never a live feed.** The only doorbell is the front door lock, a battery Tuya lock that sleeps between events. Tuya's cloud API rejects every live stream call for it (RTSP, HLS, WebRTC), and Smart Life's live view goes over a P2P link that only Tuya's mobile App SDK can open, which was judged not worth adopting. What works is the cloud: the lock pushes doorbell, unlock (with the enrolled slot), battery and alarm events, and uploads an encrypted JPEG on each press that the gateway can fetch from the album API and decrypt. So a press reaches huvu as an event with an image part, and the doorbell stays out of the feed list. Remote unlock only answers a request a visitor starts on the lock, and must always need a human tap. Full findings, API calls, the decryption layout and what was ruled out: `docs/front-door-lock.md`.
1. **Fire TV app launch: ADB, personal use only.** huvu's backend holds the Stick's one ADB connection itself (since 2026-10-17, through `adb-shell`, a pure-Python client, so the image needs no `adb` binary), and opens huvu's TV app on the first connection after the Stick boots (`open_on_boot`, see the external computer below). 1. **The external computer: the Fire TV, driven like a computer.** Decided 2026-10-17. 1. **Users and devices: a password per family member, a token per device.** Decided 2026-10-04, replacing the plan to lock the backend to the owner's email with a JWT. Users are added from the backend's command line (`uv run huvu user add`), and nobody signs up. A personal device (phone, web) logs in with its user's password. A shared device (TV, speaker) has no user and pairs instead: it shows a code that a member confirms on their phone, and it joins that member's group. Groups (added 2026-10-04) are sets of people who share devices: the household is the default group, `home`. A member trusts the group (sees its events, answers its approvals, adds shared devices to it); a guest, such as a babysitter, uses its devices and trusts nothing, so everything a guest causes needs a member's approval. Every device has its own revocable token. Each device has one conversation, so a Hermes session belongs to a user and a device, and no turn reaches another device. Phones are taken to be on their user's person, so approvals, "is it you?" questions and notifications go to phones. Each user has their own Hermes profile, so memory and skills stay per person; a group's shared devices use the group's profile (the default profile for `home`). A trigger set up from a shared device with nobody recognized waits: everyone in the group gets "is this you?" on their phone, and the first yes recognizes them at the device and makes the trigger theirs; the model is told it isn't live until then. A shared device can also recognize who is at it (a picker, the model, later voice): the person confirms on their phone, and the session then acts and logs as them without switching Hermes profile, so the prompt cache holds and their own dream reads it from the history. Each user can have an alias for each other user, such as "mom" (added 2026-10-10, `people_aliases`), asked both ways by `setup.sh` when it adds a user, and changed with `huvu user alias` or by the model (`huvu_set_person_alias`, for its own person only). An alias names one person: never a group's id, another username, or what the owner calls someone else. The model reads who is in the caller's groups by those aliases (`people_group`), and sends a person or a group a message in the caller's name (`huvu_message`, autonomy `notify`). The recipient's phone shows the sender by the recipient's own alias for them. Groups are made only from the command line; making them in the app is on `docs/v0.md`. Linking each person's own accounts (calendars and the like) is v2: one auth flow per provider, never per tool. Design: `docs/backend-architecture.md`, Users, groups and devices.
1. **Location: OwnTracks, a separate app, not a plugin in huvu's.** Decided 2026-10-06, replacing the plan for a native background-location plugin (`@capgo/background-geolocation`), which would have meant native work in the huvu app and a WebView kept alive in the background. OwnTracks already does this well on Android and iOS, and a second app on each phone was judged fine. A waypoint is a named circle (OwnTracks's word; use it, not "place" or "circle"). The phone watches its waypoints itself, so arrivals come at once; huvu holds the master list and sends each phone its waypoints in the reply to a post. An OTP before a payment stays the person's yes. The browser is headed on its profile's Bot Desktop (Xvnc) with one persistent profile, so a login stays. ## The Capacitor ceiling, and where it doesn't apply

Capacitor's WebView layer caps UI fidelity somewhat (cold start costs roughly 100-300ms of engine init, gesture/scroll feel takes deliberate CSS work to match native). This was accepted as the cost of one shared canvas implementation across every target.

On Android specifically, this ceiling does not extend to native capability. A Capacitor plugin compiles into the same APK and runs with the same OS permissions as fully native code, so wake word, widgets, and background services are exactly as capable through a plugin as they'd be in a from-scratch native app. The only real ceiling is the WebView UI surface itself.

Worth knowing if a native rewrite ever gets reconsidered for speed: Chromium's Canvas2D (used by Android's WebView and by Chrome generally) is itself implemented on top of Skia, the same rasterizer Android's native Canvas API uses. So a future native Android port of the flower canvas would be a much smaller, lower-risk job than a generic cross-platform Skia port, since it's largely the same rendering engine accessed a different way, not a different one. Not needed unless real, measured device testing says the WebView canvas isn't smooth enough.

## Chat/voice mode architecture

1. One persistent conversation (the module-level store in `chat/thread.ts`), never recreated when switching between text and voice.
1. Mode (`text` | `voice`) is app state, not a route. Switching mode must never remount the thread or drop the connection, that's what makes it feel seamless.
1. The garden canvas (`GardenCanvas`) stays mounted underneath both modes and every view at all times.
1. The UI over the canvas is a stage, not a chat log (`components/Stage.tsx`). It shows one turn (an ask and what huvu did with it) at a time, large. At launch it shows the greeting, and the turns from before wait in history; a turn takes the stage when it is asked in this session, is still running, or is a notification nobody has seen. Scrolling up folds it into a history of every turn at one size, but only once the list can't scroll any further and the gesture didn't scroll it (`stage/useScrollIntent.ts`), so reading to the top of a long answer never flips the view. Fire TV has no scroll gesture, so its D-pad up and down scroll the stage a page at a time first, and only at the edge does up fold into history. History shows every turn with chips standing in for images, live feeds and other parts. Picking a row makes it the stage again, and any scroll folds it back. Turns are the store's own model (`chat/thread.ts`): each change replaces only the turn it touches, so a streaming reply re-renders only its own turn.
1. The user's words are always sans serif: DM Sans (`font-display`), like all of huvu's running sans text, since Syne's stubby descenders made a g read as an a (changed 2026-10-07). Syne stays for the uppercase labels and the wordmark (`font-caps`, through `capsClass`). huvu's answers and notices are Newsreader, upright (`font-reading`), picked on 2026-10-07 because Bodoni's hairlines tired the eye over a paragraph; Bodoni italic stays for short display lines (the greeting, login, pairing, menu names, approval cards). Long answers are set at 18 to 20px with a 1.55 line height (`HERO_TIERS` in `TurnView.tsx`). A sent ask flies from the field up into its YOU cue, and an edited ask flies back down (`stage/flight.ts`). No element is swapped with a hard cut, everything tweens.
1. Edit on a turn is also rewind: the stage hides that turn and everything after it, and sending goes through that message's edit composer, which replaces them.
1. A notification (`notify` on the push stream) is a turn with no ask, a notice, in the same type as huvu's answers. One that arrives while a reply streams goes in under the reply, so the reply keeps the stage. Approvals and "is it you?" questions are not turns: they wait in a card pinned above the composer on phones (`components/Waiting.tsx`). The wordmark opens the menu on web and phone (`components/Menu.tsx`): the user, their triggers, their devices, pairing a shared device.
1. While a turn runs, huvu's reasoning summary shows faintly under the answer (`thinking` on the turn, never kept), and a turn that needs tools opens with one short line of huvu's own saying it's on it (the guide asks for it; the backend shows Hermes's commentary as answer text).
1. Rich parts (images, tool calls) render through a registry in `stage/parts.ts`: each tool name maps to a chip and a hero view. Unknown tools still get a chip and a one-line note. An image part comes from `ui_show_image` or from a `MEDIA:<path>` tag in huvu's answer (Hermes's own way to attach a file, such as its browser's screenshot), which the backend takes out of the text (added 2026-10-09). Either names an image by a source's ref, an absolute path on the host's disk, or an https URL. Any path works, and the backend serves a file only while its first bytes say it's an image, so a secret never leaves (`media.py`). One image shows whole, several show as tiles. A live video feed (huvu's browser, a camera, a screen) is one generic part, `video_feed`, whose `src` is a WHEP endpoint: the client POSTs a WebRTC offer there, plays the answer's video in a muted `<video>`, and DELETEs the session's Location to hang up (`stage/useWhepFeed.ts`). WebRTC was picked over MJPEG (a whole image per frame, several times the bandwidth, software decode) and over HLS/DASH (seconds of latency), since a live view has one viewer who wants it now, the way a CCTV live view does. WHEP keeps the part generic: any WHEP server works, including a media server such as mediamtx relaying a camera's RTSP. Only the turn on the stage holds its feed open.
1. Voice mode moves the flower (`components/VoiceFlower.tsx`) to the middle of the screen and hides the text field. On phone it also fades out huvu's answer text above the flower (`voiceAnswerText`), since huvu says it anyway; the ask, rich parts and a stopped/failed note stay. The flower grows with the user's mic level; huvu's voice drives the garland. Scrolling the stage in voice mode (wheel or touch) docks the flower, composer-sized, at the bottom so the turn gets the screen; tapping it, pressing the talk key (space on web), or speaking while it listens brings it back to the middle. Hands-free from the flower, on every target: an ask ends after 3s of quiet, talking over huvu cuts it off, and it listens again by itself after huvu speaks. Push-to-talk by holding space (web) is its own mode: release sends, a pause while holding is fine, huvu's answer never starts a listen, and only holding space again cuts huvu off (no barge-in). Space on the focused flower is push-to-talk too, never a press. Fire TV never enters voice mode, and says every answer without it. Enter sends on web, phone sends only with its send button. These per-target input rules live in `interaction.ts` next to the mode maps.
1. Every ask carries how it was made (`mode`: `voice` or `text`), and the backend tells the model in one line before the message, so a spoken answer comes without emojis or markdown (`VOICE_NOTE` in `prompts.py`). The voice also drops any emoji that slips through (`speakable` in `speech.py`).
1. Speech to text: the app records the ask from the shared mic and the backend transcribes it (Groq's Whisper, see the speech decision). Without a key it falls back to the browser's Web Speech API (desktop Chrome), or, in a dev build only, a mock of fixed phrases (`voice/transcriber.ts`); any other build says it can't hear. While the backend doesn't answer, nothing listens, and the hint under the flower says so. huvu's voice streams from the backend sentence by sentence and plays gapless (`voice/speaker.ts`).
1. Audio is latency-first. One `AudioContext` for the whole app (`voice/audio.ts`), resumed inside the gesture that enters voice. One shared mic stream (`voice/mic.ts`) serves the flower's level meter and barge-in, and lingers 8s after its last user so the next listen or reply skips `getUserMedia`; leaving voice mode closes it at once. Hands-free holds it from the flower's tap until it stops listening (`useVoiceSession.ts`), since Android opens the mic in call mode and going in or out of it moves the speaker's output, which cut the first seconds of huvu's answer (found 2026-10-10: the mic used to close during a long think and open again for barge-in as the first sentence played). huvu's voice (`voice/speaker.ts`) streams from the backend as one MP3 clip per sentence; each is decoded in order and scheduled right after the one before, so sentences play without gaps. `speak(turnId, bargeIn)` resolves when the last sentence ends or, hands-free only, the user talks over it.
1. The garden engine is plain imperative code in `canvas/garden.ts`, outside React; `GardenCanvas` only mounts it, through `canvas/host.ts`. It paints in a Web Worker (`canvas/worker.ts`) on an `OffscreenCanvas` the page hands over, and on the page only where a browser can't do that or the worker fails to start. huvu's voice is read on the page (`speaker.sampleVoice()`) and sent to the worker each frame while it plays; written replies feed it through `growForWords()`. The loop sleeps once nothing is left to paint, and wakes on either input. p5.brush starts loading at boot, in parallel with React's first render. What it paints stays: there is no fade. Tuned on a mid-range Android phone on 2026-10-10, where the garden made typing lag by up to a second. Three things fixed it, each measured on the phone: the page-wide wash toward paper, and the wash over old flowers, both went, since neither changed a visible pixel and each page wash stalled the phone's GPU for about half a second; the worker keeps p5.brush's frames (over 20ms each there) off the page's thread; and in the worker, p5.brush's own 2D canvases are kept in memory (`willReadFrequently`), since on the GPU they loaded the process that also draws the page. With all three, typing with the garden painting matches typing without it. The bench that measured it: `canvas/bench.ts` and `frontend/bench/`.
1. Motion loads its animation features lazily (`LazyMotion` in `App.tsx`, `motionFeatures.ts`), so components use `m.*` from `motion/react-m`, never `motion.*`. `strict` mode throws if a `motion.*` component slips in.
1. Platform/UI-shape config lives in one file, `frontend/src/config/interaction.ts`: a `Target` (`web` | `phone` | `firetv`) read from a build-time `VITE_TARGET` env var, and one `Profile` per target in a single table (whether the screen has input of its own, default mode, whether mode is switchable, Enter/send-button rules, push-to-talk key, feeds key, hint copy, launch greetings, flower size, whether voice mode shows the answer text, garden pixel density). Code reads the resolved profile as `ui`, never indexes by `TARGET`. The web build opened on a touch screen (a phone's browser: its main pointer is `coarse`; a fine one beside it is allowed since 2026-10-17, for the owner's dad's Galaxy Ultra and its pen) resolves to the phone's profile with `deviceKind` left as `web` (added 2026-10-09): it looks like a phone, so no space to talk, a send button and no focus grabbing, and to the backend it is still a browser. Opened from the home screen (`display-mode: standalone`), it is a phone to the backend too (added 2026-10-11), since the backend sends notifications, approvals and "is it you?" questions only to phones, and only a phone may answer them or pair. Web and phone default to text and allow switching. Fire TV has `hasInput: false`: no composer, no flower, no voice mode, no edit or retry; `speaksAnswers` says every answer aloud. It can still send a choice: down reaches the choices once the turn has scrolled to its end, left and right walk them, up leaves them, and select sends one as an ask.
1. `Target` is intentionally not the same thing as OS platform (`Capacitor.getPlatform()`, `ios` | `android` | `web`). `Target` answers "what does this screen look like" (phone collapses iOS and Android together, since they need the same UI default). OS platform answers "what can this device actually do" (wake word being Android-only is gated on platform, not on `Target`). Keep these two checks separate, don't fold one into the other.
1. `VITE_TARGET` has no default and no fallback. Missing or invalid values throw at runtime (`resolveTarget()` in `interaction.ts`). Every dev/build script names its target explicitly: `dev:web`, `dev:phone`, `dev:firetv`, `build:web`, `build:phone`, `build:firetv`.
1. The phone home-screen widget's quick-voice button is meant to deep-link into the app with a `?mode=voice` query param, read once on launch by `initialMode()`. Not yet wired to a real widget, that part still needs the native widget extension above.

## Prompts

Every text a model reads from huvu lives in `backend/src/huvu/prompts.py` (moved there 2026-10-08): the plugin's guide, the MCP instructions, tool and schema descriptions, every source's descriptions and guide (`TEXT`, keyed by where each sits in its spec, such as `location.value.place`), the skill renderer, wakes, the situation block, the note that continues a session, the dream and Whisper's prompt. Code elsewhere picks a text and fills its blanks. No text a model reads carries examples (the owner's rule, 2026-10-13): a model fixes on the one case an example shows and misses what the text means, so each text states its intent and nothing more. New model-facing text goes there too, including a new driver's. Error messages stay where they are raised. `prompts.py` imports nothing from huvu, because the Hermes plugin loads it by path inside Hermes's Python. `SOUL.md` stays a file at the repo root. `tests/test_prompts.py` pins the texts built at run time.

## Sanity checklist

Every new feature that a person touches, and every change to how one behaves, gets a check in `docs/sanity-check.md` in the same change. Write it for humans, not developers: what to do, and what they should see. Put it under the screen or feature it belongs to. Move it out of "What doesn't work yet" once it works.
