# huvu

An agent chat app. The core idea: the whole UI is a canvas built with p5.brush. As the agent talks, flowers grow in. The canvas is the last thing to build, since it needs a palette decided first, and it's the most creative part.

Talks to an agent called Hermes on the backend. Used by one family: each person is a user, and shared devices (the TV, speaker hardware still to be built) belong to a group, the household by default. Hosted on the web, and installed as an app on phone and Fire TV.

## Platforms and priorities

1. Phone (Android): the daily driver. Needs the most native flexibility: wake word, widgets, background location, fast cold start. This is the platform to optimize hardest for.
1. Web: hosted, full-featured, same codebase as phone.
1. Phone (iOS): minimal, chat only. Built for the owner's mom. Platform limitations here (see wake word below) are accepted, not worked around.
1. Fire TV: display only, the largest screen, so it gets the most design care. The app takes no voice and no text. It shows the turns of its own conversation and the live feeds picked on it with the remote (Menu opens the list, which also says who is here). Fire TV gives apps no mic anyway: the remote's mic button always goes to Alexa, and Fire TV has no speech recognizer for apps. So asks come in through a custom Alexa skill: "Alexa, ask huvu ...". Alexa only carries the request, and its spoken response is always empty or "done". The gateway brings the app to the front over ADB (see stack decisions), and the app shows the turn. How the ask gets from the skill to the app is not decided yet. On launch, the empty stage shows one greeting picked at random, with an example Alexa ask under it (`greetings` in `interaction.ts`). Treated as its own build target.

## Stack decisions and why

1. **Frontend shell: Capacitor, not React Native.** p5.brush only exists as a browser Canvas2D library, and the flower visuals must look identical across web, phone, and Fire TV. Porting p5.brush's stroke/noise rendering to a native engine (react-native-skia) was priced out as a multi-month job with ongoing visual-drift risk, worse than the cost of any Capacitor limitation. Capacitor wraps the same web app for every target, so there's one implementation of the canvas, not several that have to be kept in sync.
1. **Chat state: a small hand-written store, not assistant-ui.** `frontend/src/chat/thread.ts` holds the conversation as turns (one ask and what huvu did with it), since the stage shows turns and never a chat log. assistant-ui was used at first, for its thread runtime only; it was dropped because it was more than half of the startup bundle (602 KB down to 335 KB) and every turn had to be derived from its messages on each change. Edit is rewind: it replaces the turn and everything after it, with no branches kept. The store mints each turn's id and sends it with the ask, so the backend keeps the same id. Each turn has its own stream: stop asks the backend and keeps reading until the turn ends, and a turn the store has no stream of (one running across a restart, one the device didn't start) is followed from its start (`GET /api/turns/{id}/events`), since a delta can't be added to a snapshot. The store catches up from `GET /api/conversation` each time the push stream connects. The backend calls, Server-Sent Events streams, live in `chat/backend.ts`.
1. **Backend: Python (uv, asyncio, Pydantic, FastAPI, SQLite), not Node or Bun.** JS/TS everywhere was the first pick, to avoid a language switch when reviewing code. It was reversed on 2026-10-03: the backend will need ML pieces that ship as Python first (face embeddings, speech, vision), Hermes is Python and its plugins are too, and the tested Tuya code is Python. The backend stays one language. Its job: an interface to data (pluggable sources, state, an event log, data triggers, the action policy), exposed to Hermes over MCP, and the link to the frontend (sessions, turning Hermes output into parts). It owns nothing about the model; prompts, memory, schedules and the nightly dream belong to Hermes. Design: `docs/backend-architecture.md`. The frontend side: `docs/frontend-contract.md`.
1. **Data: everything is SQLite, and the agent learns preferences from it.** Decided 2026-10-06. huvu's agent is expected to learn each person's preferences on its own, mostly in the nightly dream, through real data engineering over the house's history. Every source declares history tables in its spec and records typed rows (`ctx.record`); the kernel keeps them all in one SQLite file (`data/analytics.db`), adds the same time and person columns to every row, and keeps them for good. The `data_sql` tool runs one read-only, caller-scoped SQLite query over them and the event log, so one query can join sources. No other database engine is used; extensions cover the rest (FTS5, JSON, `sqlite-vec` later). Non-tabular data (images, audio) stays in its source, and the rows hold facts about it with a ref. Design: `docs/backend-architecture.md`, History tables.
1. **Home Assistant: the household's scripts are huvu's only way to work devices.** Decided 2026-10-06. Most devices are infrared (a Broadlink RM4 pressing buttons in sequence), so the abstraction lives in HA: every way huvu may change the house is an HA script with a description, fields and an area, exposed to Assist. Each exposed script is one huvu action (`script.bedroom_ac_set` is `ha_bedroom_ac_set`); a label on it (`huvu_silent`, `huvu_notify`, `huvu_ask`, `huvu_human`) sets its autonomy, and no label means ask. huvu reads only what is exposed to Assist, records who caused every change (huvu, an HA app user, an automation, the device), and picks up script changes without a restart. Driver: `backend/src/huvu_drivers/ha/`. Design: `docs/backend-architecture.md`, The Home Assistant driver. The HA side, for the agents that set it up: `docs/home-assistant.md`.
1. **Live feeds: the gateway lists them, and nothing opens until picked.** The gateway knows every feed that exists (cameras, huvu's browser, a screen) and publishes that list, so the model has it as context and the app can offer it. A listed feed is not an open one. A feed opens only when the model picks it in a tool call, which emits a `video_feed` part, or when the user picks it. This keeps bandwidth and decoders idle until someone wants a feed, and it fits the stage rule that only the turn on the stage holds its feed open. Face recognition, if the camera side does it, reaches the model as text context next to the feed. `GET /api/feeds` is the list. In the frontend, `chat/feeds.ts` holds the list, fetched at boot and again each time it opens. `components/Feeds.tsx` shows it as a `LIVE / n` control opposite the wordmark, text only, with no previews, since a preview would be an open feed. On a shared device the same list has a "who's here" section, for recognizing the person at it. Picking a feed only watches it, and huvu is never asked (`thread.watch()`): it makes a turn of its own with no ask, the feed's name as the answer and the feed as its one part. Such a turn has `Turn.feed` set and makes no call of its own. The next ask carries it to the backend as an action (`{text, at}`, such as "opened the live feed balcony"), which Hermes reads as context and never answers (`actionsAfterLastAsk()` in `thread.ts`). A reply still coming in keeps streaming into its own turn underneath. A feed opened by huvu in a tool call is a different thing: a `video_feed` part in huvu's answer, and what huvu says about it (who is at the door) is entirely up to the agent. Fire TV opens the list with its Menu button (`feedsKey` in `interaction.ts`).
1. **Doorbell: a snapshot per press, never a live feed.** The only doorbell is the front door lock, a battery Tuya lock that sleeps between events. Tuya's cloud API rejects every live stream call for it (RTSP, HLS, WebRTC), and Smart Life's live view goes over a P2P link that only Tuya's mobile App SDK can open, which was judged not worth adopting. What works is the cloud: the lock pushes doorbell, unlock (with the enrolled slot), battery and alarm events, and uploads an encrypted JPEG on each press that the gateway can fetch from the album API and decrypt. So a press reaches huvu as an event with an image part, and the doorbell stays out of the feed list. Remote unlock only answers a request a visitor starts on the lock, and must always need a human tap. Full findings, API calls, the decryption layout and what was ruled out: `docs/front-door-lock.md`.
1. **Fire TV app launch: ADB from the gateway, personal use only.** When a turn is sent to the TV, the gateway runs `am start` on the Fire TV over ADB, so huvu comes to the front even while Netflix plays. The other paths were ruled out. A custom skill can't launch an Android app. Alexa for Apps opens apps on phones only. A Video Skills Kit skill can launch apps but takes no free-form text. Having Alexa itself run "open huvu" needs an unofficial API, and people report that Alexa fails to open sideloaded apps. ADB needs the gateway on the TV's network (or a tunnel to it), ADB debugging on, and the gateway's key approved once on the TV. Port 5555 must never be reachable from the internet. A pure-Python ADB client (`adb-shell`, untried) would mean the backend needs no `adb` binary. Fire OS updates may turn developer options off. None of this can ship as a product. The product path is the phone as mic and remote, launching the TV app through Matter Casting (Fire TV) or Google Cast (Google TV).
1. **Users and devices: a password per family member, a token per device.** Decided 2026-10-04, replacing the plan to lock the backend to the owner's email with a JWT. Users are added from the backend's command line (`uv run huvu user add`), and nobody signs up. A personal device (phone, web) logs in with its user's password. A shared device (TV, speaker) has no user and pairs instead: it shows a code that a member confirms on their phone, and it joins that member's group. Groups (added 2026-10-04) are sets of people who share devices: the household is the default group, `home`. A member trusts the group (sees its events, answers its approvals, adds shared devices to it); a guest, such as a babysitter, uses its devices and trusts nothing, so everything a guest causes needs a member's approval. Every device has its own revocable token. Each device has one conversation, so a Hermes session belongs to a user and a device, and no turn reaches another device. Phones are taken to be on their user's person, so approvals, "is it you?" questions and notifications go to phones. Each user has their own Hermes profile, so memory, skills and cron jobs stay per person; a group's shared devices use the group's profile (the default profile for `home`). A trigger set up from a shared device with nobody recognized waits: everyone in the group gets "is this you?" on their phone, and the first yes recognizes them at the device and makes the trigger theirs; the model is told it isn't live until then. A shared device can also recognize who is at it (a picker, the model, later voice): the person confirms on their phone, and the session then acts and logs as them without switching Hermes profile, so the prompt cache holds and their own dream reads it from the event log. Linking each person's own accounts (calendars and the like) is v2: one auth flow per provider, never per tool. Design: `docs/backend-architecture.md`, Users, groups and devices.
1. **Background location: coarse, low priority, native plugin required.** Browser `geolocation.watchPosition` gets suspended when the app backgrounds, so this needs a native background-location plugin, not JS. Given the "don't really care, keep it coarse" requirement, use the platform's native significant-location-change mode (large distance filter, low accuracy) rather than Transistorsoft's full paid engine. `@capgo/background-geolocation` is the free option that covers this.
1. **Wake word: Android only, by platform policy, not by choice.** `@capacitor-community/porcupine-wake-word` (Picovoice Porcupine) gives on-device, power-efficient always-listening detection via a foreground service. iOS does not allow arbitrary apps continuous background microphone access the way Android does, this is a hard platform limit, not something to build around. Given the iOS build is chat-only for the owner's mom, this gap doesn't matter there.
1. **Push notifications: `@capacitor-firebase/messaging` alone, for FCM (APNs behind it on iOS).** The official Push Notifications plugin was the first pick next to it, but the plugin's README presents the two as alternatives, and each registers its own FCM service on Android. The backend sends notifications, pending approvals and "is it you?" questions to the phone's FCM token whether or not the app is open, since a backgrounded WebView can keep the push stream open for a while. The OS shows the app in front no notification, so nothing shows twice (`account/nativePush.ts`, `backend/src/huvu/native_push.py`).
1. **Camera and gallery:** `@capacitor/camera`, native picker, no custom work needed.
1. **Widgets:** genuinely native code on both platforms (SwiftUI WidgetKit on iOS, Glance/RemoteViews on Android), no library replaces this. A Capacitor plugin (e.g. `capacitor-widgetsbridge-plugin` on iOS) only bridges data into a widget extension that still has to be hand-written. Not started.

## The Capacitor ceiling, and where it doesn't apply

Capacitor's WebView layer caps UI fidelity somewhat (cold start costs roughly 100-300ms of engine init, gesture/scroll feel takes deliberate CSS work to match native). This was accepted as the cost of one shared canvas implementation across every target.

On Android specifically, this ceiling does not extend to native capability. A Capacitor plugin compiles into the same APK and runs with the same OS permissions as fully native code, so wake word, widgets, and background services are exactly as capable through a plugin as they'd be in a from-scratch native app. The only real ceiling is the WebView UI surface itself.

Worth knowing if a native rewrite ever gets reconsidered for speed: Chromium's Canvas2D (used by Android's WebView and by Chrome generally) is itself implemented on top of Skia, the same rasterizer Android's native Canvas API uses. So a future native Android port of the flower canvas would be a much smaller, lower-risk job than a generic cross-platform Skia port, since it's largely the same rendering engine accessed a different way, not a different one. Not needed unless real, measured device testing says the WebView canvas isn't smooth enough.

## Chat/voice mode architecture

1. One persistent conversation (the module-level store in `chat/thread.ts`), never recreated when switching between text and voice.
1. Mode (`text` | `voice`) is app state, not a route. Switching mode must never remount the thread or drop the connection, that's what makes it feel seamless.
1. The garden canvas (`GardenCanvas`) stays mounted underneath both modes and every view at all times.
1. The UI over the canvas is a stage, not a chat log (`components/Stage.tsx`). It shows one turn (an ask and what huvu did with it) at a time, large. At launch it shows the greeting, and the turns from before wait in history; a turn takes the stage when it is asked in this session, is still running, or is a notification nobody has seen. Scrolling up folds it into a history of every turn at one size, but only once the list can't scroll any further and the gesture didn't scroll it (`stage/useScrollIntent.ts`), so reading to the top of a long answer never flips the view. Fire TV has no scroll gesture, so its D-pad up and down scroll the stage a page at a time first, and only at the edge does up fold into history. History shows every turn with chips standing in for images, live feeds and other parts. Picking a row makes it the stage again, and any scroll folds it back. Turns are the store's own model (`chat/thread.ts`): each change replaces only the turn it touches, so a streaming reply re-renders only its own turn.
1. The user's words are always sans serif (Syne), huvu's are Bodoni italic. A sent ask flies from the field up into its YOU cue, and an edited ask flies back down (`stage/flight.ts`). No element is swapped with a hard cut, everything tweens.
1. Edit on a turn is also rewind: the stage hides that turn and everything after it, and sending goes through that message's edit composer, which replaces them.
1. A notification (`notify` on the push stream) is a turn with no ask, a notice, in Bodoni like everything huvu says. One that arrives while a reply streams goes in under the reply, so the reply keeps the stage. Approvals and "is it you?" questions are not turns: they wait in a card pinned above the composer on phones (`components/Waiting.tsx`). The wordmark opens the menu on web and phone (`components/Menu.tsx`): the user, their triggers, their devices, pairing a shared device.
1. Rich parts (images, tool calls) render through a registry in `stage/parts.ts`: each tool name maps to a chip and a hero view. Unknown tools still get a chip and a one-line note. A live video feed (huvu's browser, a camera, a screen) is one generic part, `video_feed`, whose `src` is a WHEP endpoint: the client POSTs a WebRTC offer there, plays the answer's video in a muted `<video>`, and DELETEs the session's Location to hang up (`stage/useWhepFeed.ts`). WebRTC was picked over MJPEG (a whole image per frame, several times the bandwidth, software decode) and over HLS/DASH (seconds of latency), since a live view has one viewer who wants it now, the way a CCTV live view does. WHEP keeps the part generic: any WHEP server works, including a media server such as mediamtx relaying a camera's RTSP. Only the turn on the stage holds its feed open.
1. Voice mode moves the flower (`components/VoiceFlower.tsx`) to the middle of the screen and hides the text field. On phone it also fades out huvu's answer text above the flower (`voiceAnswerText`), since huvu says it anyway; the ask, rich parts and a stopped/failed note stay. The flower grows with the user's mic level; huvu's voice drives the garland. Scrolling the stage in voice mode (wheel or touch) docks the flower, composer-sized, at the bottom so the turn gets the screen; tapping it, pressing the talk key (space on web), or speaking while it listens brings it back to the middle. Hands-free from the flower, push-to-talk by holding space (web). Fire TV never enters voice mode. Enter sends on web, phone sends only with its send button. These per-target input rules live in `interaction.ts` next to the mode maps.
1. Speech to text uses the browser's Web Speech API where it exists (desktop Chrome) and a mock of fixed phrases elsewhere (`voice/transcriber.ts`), until a real STT service sits behind the gateway.
1. Audio is latency-first. One `AudioContext` for the whole app (`voice/audio.ts`), resumed inside the gesture that enters voice. One shared mic stream (`voice/mic.ts`) serves the flower's level meter and barge-in, and lingers 8s after its last user so the next listen or reply skips `getUserMedia`; leaving voice mode closes it at once. huvu's voice (`voice/speaker.ts`) is decoded once and cached, preloaded when voice starts. `speak()` resolves when the clip ends or the user talks over it.
1. The garden engine is plain imperative code in `canvas/garden.ts`, outside React; `GardenCanvas` only mounts it. It reads huvu's voice from `speaker.sampleVoice()` each frame, and written replies feed it through `growForWords()`. The loop sleeps once nothing is left to paint or fade, and wakes on either input. p5.brush starts loading at boot, in parallel with React's first render.
1. Motion loads its animation features lazily (`LazyMotion` in `App.tsx`, `motionFeatures.ts`), so components use `m.*` from `motion/react-m`, never `motion.*`. `strict` mode throws if a `motion.*` component slips in.
1. Platform/UI-shape config lives in one file, `frontend/src/config/interaction.ts`: a `Target` (`web` | `phone` | `firetv`) read from a build-time `VITE_TARGET` env var, and one `Profile` per target in a single table (whether the screen has input of its own, default mode, whether mode is switchable, Enter/send-button rules, push-to-talk key, feeds key, hint copy, launch greetings, flower size, whether voice mode shows the answer text, garden pixel density). Code reads the resolved profile as `ui`, never indexes by `TARGET`. Web and phone default to text and allow switching. Fire TV has `hasInput: false`: no composer, no flower, no voice, no edit or retry. It can still send a choice: down reaches the choices once the turn has scrolled to its end, left and right walk them, up leaves them, and select sends one as an ask.
1. `Target` is intentionally not the same thing as OS platform (`Capacitor.getPlatform()`, `ios` | `android` | `web`). `Target` answers "what does this screen look like" (phone collapses iOS and Android together, since they need the same UI default). OS platform answers "what can this device actually do" (wake word being Android-only is gated on platform, not on `Target`). Keep these two checks separate, don't fold one into the other.
1. `VITE_TARGET` has no default and no fallback. Missing or invalid values throw at runtime (`resolveTarget()` in `interaction.ts`). Every dev/build script names its target explicitly: `dev:web`, `dev:phone`, `dev:firetv`, `build:web`, `build:phone`, `build:firetv`.
1. The phone home-screen widget's quick-voice button is meant to deep-link into the app with a `?mode=voice` query param, read once on launch by `initialMode()`. Not yet wired to a real widget, that part still needs the native widget extension above.

## Sanity checklist

Every new feature that a person touches, and every change to how one behaves, gets a check in `docs/sanity-check.md` in the same change. Write it for humans, not developers: what to do, and what they should see. Put it under the screen or feature it belongs to. Move it out of "What doesn't work yet" once it works.

## Known gaps / not yet done

1. Backend drivers: the kernel is built and tested (`uv run pytest` in `backend/`), and it has never run against a live Hermes. The only driver is Home Assistant, tested against a fake HA only; the HA side (scripts, labels, exposure, power plugs) is not set up yet, see `docs/home-assistant.md`. The Tuya driver doesn't exist. The dream prompt that uses the history tables is not written. Hermes was updated to v0.21.5+ on 2026-10-04; its API server and the per-user profiles are not set up yet. The frontend speaks the whole contract in `docs/frontend-contract.md`: auth, chat, the push stream, approvals, attendance. It was checked end to end against the real kernel with a scripted Hermes, not against a live Hermes. Live feeds go out as a `video_feed` tool part pointing at a WHEP URL; the WHEP POST carries the bearer token when the feed is on the backend's own origin. The backend's WebRTC stack is not chosen yet (aiortc is the obvious Python option, untried), so no WHEP endpoint exists and no feed can play. Chat needs Hermes behind the backend; there is no stand-in.
1. Real speech: STT is Web Speech or a mock (`voice/transcriber.ts`), and huvu's voice is one bundled test clip (`public/audio/test-voice.m4a`).
1. Wake word, background location, widgets: all scoped and libraries picked, none implemented.
1. Native push is built on both sides but has never sent a real message: no Firebase project exists yet, so there is no `google-services.json` and no service account key for `HUVU_FCM_CREDENTIALS`. What else the frontend still lacks is in `docs/frontend-changes.md`.
1. Android Studio is installed on the dev laptop, with its bundled JDK (`/Applications/Android Studio.app/Contents/jbr/Contents/Home`); there is no system `java`, so Gradle needs `JAVA_HOME` set to it. `npx cap sync android` has run with all four plugins (app, preferences, secure storage, Firebase messaging). No APK has been built yet: the first `./gradlew assembleDebug` timed out downloading Gradle.
1. Phone and Fire TV builds have only been exercised in a desktop browser (`dev:phone`, `dev:firetv`), never on hardware. Unverified: the keyboard resizing the phone WebView, Fire TV's select button arriving as Enter, its Menu button arriving as ContextMenu, D-pad focus rings at TV distance.
1. Fire TV: `LEANBACK_LAUNCHER` manifest entry not added yet. WebRTC playback of live feeds there hasn't been verified on real hardware.
1. Fire TV: the Alexa skill is not registered, so nothing asks on the TV yet (the push stream would show such a turn), and the ADB launch is not built. Pairing and "who's here" are built. Its visual pass is on the design board (row E, "Fire TV, display only"; 4a picked for watching a feed). Only the launch greeting and the feed caption are built; the rest still uses web sizes.
1. iOS build not attempted yet.
